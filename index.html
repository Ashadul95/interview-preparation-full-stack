NODE PRODUCTION — Rate Limiting, Resilience and Incident Questions

How do you implement rate limiting in Express?

Rate limiting protects an API by counting requests for a chosen identity, such as an authenticated user, API key, or client IP, inside a time window. A single-process in-memory counter is acceptable for a local demo but fails when several Node instances share traffic. In production, use a shared Redis store, return HTTP 429, include a retry hint when useful, and apply stricter limits to login, password reset, search, and payment endpoints than to normal reads.
Step by step: (1) Identify the caller key. (2) Decide the policy, for example 100 general requests per minute and 5 login attempts per 15 minutes. (3) Increment an atomic Redis counter with an expiry. (4) Reject before expensive business logic when the limit is exceeded. (5) Emit metrics for allowed, blocked, and Redis-failure requests. (6) Decide whether a Redis outage should fail closed for login or fail open for low-risk reads.
import rateLimit from 'express-rate-limit';
import RedisStore from 'rate-limit-redis';
import { redis } from './redis.js';

const apiLimiter = rateLimit({
	windowMs: 60 * 1000,
	limit: 100,
	standardHeaders: 'draft-7',
	legacyHeaders: false,
	keyGenerator: request => request.user?.id || request.ip,
	store: new RedisStore({ sendCommand: (...args) => redis.sendCommand(args) }),
	handler: (request, response) => {
		response.status(429).json({
			code: 'RATE_LIMITED',
			message: 'Too many requests. Try again later.'
		});
	}
});

const loginLimiter = rateLimit({
	windowMs: 15 * 60 * 1000,
	limit: 5,
	standardHeaders: 'draft-7'
});

app.use('/api', apiLimiter);
app.post('/auth/login', loginLimiter, loginHandler);
Interview trade-off: Fixed windows are simple but allow bursts at a boundary. Sliding-window or token-bucket algorithms smooth traffic better. A distributed limiter must use atomic Redis operations, avoid trusting arbitrary forwarded IP headers, and preserve availability with an explicit cache-failure policy.

What is the difference between IP, user, API-key, and endpoint rate limits?

An IP limit protects against anonymous floods but can punish many users behind one NAT. A user limit is fairer after authentication. An API-key limit supports partner quotas and billing. An endpoint limit protects expensive operations such as login, exports, search, and report generation. Senior designs usually combine them: a global edge limit, an identity limit, and a route-specific limit.
Production scenario: If one customer reports 429 responses, inspect the effective key, proxy configuration, shared NAT behavior, Redis latency, and endpoint policy before simply raising the limit. Compare p95 latency, blocked requests, and downstream saturation.

How do you make a Node.js API resilient in production?

Set timeouts on every outbound request, validate configuration at startup, use bounded retries only for transient and idempotent operations, add circuit breakers around unhealthy dependencies, limit payload size, avoid synchronous CPU work, use graceful shutdown, and expose readiness separately from liveness. A retry without a timeout or idempotency policy can multiply an outage.

ADVANCED ASYNC PATTERNS — Throttling, Debouncing and Backpressure

Debounce vs throttle: what is the difference and when do you use each?

Debounce waits until events stop for a quiet period, so it is ideal for search input, validation, and autosave. Throttle allows at most one action during a time window, so it is useful for scroll, resize, mouse movement, telemetry, and rate-controlled UI updates. The decision depends on whether the latest event should win after the burst or whether regular intermediate updates are needed.
Production scenario: A search box should debounce so typing angular does not send seven requests. A scroll listener should throttle so the page can update a progress indicator without running layout work hundreds of times per second. For network search also use cancellation so an older response cannot overwrite a newer result.
function debounce(callback, delayMs) {
	let timer;
	return (...args) => {
		clearTimeout(timer);
		timer = setTimeout(() => callback(...args), delayMs);
	};
}

function throttle(callback, intervalMs) {
	let lastRun = 0;
	return (...args) => {
		const now = Date.now();
		if (now - lastRun >= intervalMs) {
			lastRun = now;
			callback(...args);
		}
	};
}

input.addEventListener('input', debounce(search, 300));
window.addEventListener('scroll', throttle(updateProgress, 100));

What is backpressure in a Node.js service?

Backpressure means slowing or buffering a producer when a consumer cannot keep up. Without it, a fast file, socket, queue consumer, or request stream can grow memory usage until the process becomes unhealthy. Node streams expose backpressure through write() returning false and the drain event; queues use visibility, concurrency, rate limits, and bounded retries.

How do you choose concurrency for workers?

Start from the bottleneck and its limits, not an arbitrary number. Measure CPU, memory, downstream connection limits, queue age, processing latency, and error rate. Increase concurrency until throughput improves without causing timeouts or saturation. Bound concurrency per worker, use a dead-letter policy for poison jobs, and make each job idempotent because retries and crashes are normal.

What is the difference between a Signal and an Observable?

A Signal represents current synchronous state and is read by calling it. A computed Signal derives synchronously from other Signals. An Observable represents a stream over time and is better for HTTP, websockets, user events, cancellation, retries, and composition. Use an explicit boundary such as toSignal or toObservable rather than mixing ownership casually.

Explain switchMap, mergeMap, concatMap and exhaustMap with use cases.

Valid parentheses

Two Sum with a hash map

Interview answer: Store each previously seen value and its index in a Map. At index i, the required partner is target - numbers[i]. Check for that partner before storing the current value so an element is never reused. This changes the brute-force O(n²) pair search into average O(n) time with O(n) extra space.
Dry run: For [2,7,11,15] and target 9: index 0 has 2, partner 7 is absent, so store 2 → 0. Index 1 has 7, partner 2 is present at index 0, so return [0,1]. For duplicates such as [3,3] target 6, the first 3 is stored and the second 3 finds it.
function twoSum(numbers, target) {
	const indexByValue = new Map();

	for (let index = 0; index < numbers.length; index += 1) {
		const partner = target - numbers[index];
		if (indexByValue.has(partner)) {
			return [indexByValue.get(partner), index];
		}
		indexByValue.set(numbers[index], index);
	}

	return [];
}

twoSum([2, 7, 11, 15], 9); // [0, 1]

Longest substring without repeating characters

Use a sliding window with a left boundary and a map of each character's latest index. When a repeated character appears inside the current window, move the left boundary beyond its previous position. Each character is visited a bounded number of times, so time is O(n) and space is O(k).
Dry run: For abcabcbb, the window grows a, ab, abc. The next a moves left from 0 to 1, giving bca. Continue this way; the maximum length is 3.
function longestUniqueSubstring(text) {
	const lastSeen = new Map();
	let left = 0;
	let best = 0;

	for (let right = 0; right < text.length; right += 1) {
		const character = text[right];
		if (lastSeen.has(character)) {
			left = Math.max(left, lastSeen.get(character) + 1);
		}
		lastSeen.set(character, right);
		best = Math.max(best, right - left + 1);
	}
	return best;
}

Merge overlapping intervals

Sort intervals by start time. Keep the last merged interval. If the next start is at or before the current end, extend the end; otherwise start a new merged interval. Sorting dominates the complexity: O(n log n) time and O(n) output space.
Dry run: [[1,3],[2,6],[8,10],[9,12]] becomes [1,6], then [8,12]. The second interval overlaps the first; the fourth overlaps the third.
function mergeIntervals(intervals) {
	const sorted = [...intervals].sort((a, b) => a[0] - b[0]);
	const merged = [];
	for (const interval of sorted) {
		const previous = merged[merged.length - 1];
		if (!previous || interval[0] > previous[1]) {
			merged.push([...interval]);
		} else {
			previous[1] = Math.max(previous[1], interval[1]);
		}
	}
	return merged;
}

Binary tree level-order traversal

Use a queue for breadth-first traversal. At each level capture the queue length before processing so children added during this level belong to the next level. Time is O(n) and space is O(w), where w is the maximum tree width.
function levelOrder(root) {
	if (!root) return [];
	const result = [];
	const queue = [root];
	let head = 0;

	while (head < queue.length) {
		const levelSize = queue.length - head;
		const level = [];
		for (let index = 0; index < levelSize; index += 1) {
			const node = queue[head++];
			level.push(node.value);
			if (node.left) queue.push(node.left);
			if (node.right) queue.push(node.right);
		}
		result.push(level);
	}
	return result;
}

Kth largest element in an array

Interview answer: For a reusable and easy-to-explain solution, maintain a min-heap of size k. The heap contains the best k values seen so far, and its smallest value is the kth largest overall. If a new value is larger than the heap minimum, remove the minimum and insert the new value. This avoids sorting the complete array and uses O(n log k) time and O(k) space.
Dry run: Input [3,2,1,5,6,4], k = 2. Keep [3], then [2,3]. Value 1 is ignored. Value 5 replaces 2, giving [3,5]. Value 6 replaces 3, giving [5,6]. Value 4 is ignored. The heap minimum is 5, so the answer is 5.
class MinHeap {
	constructor() { this.values = []; }
	peek() { return this.values[0]; }
	push(value) {
		this.values.push(value);
		let index = this.values.length - 1;
		while (index > 0) {
			const parent = Math.floor((index - 1) / 2);
			if (this.values[parent] <= this.values[index]) break;
			[this.values[parent], this.values[index]] = [this.values[index], this.values[parent]];
			index = parent;
		}
	}
	pop() {
		const minimum = this.values[0];
		const last = this.values.pop();
		if (this.values.length) {
			this.values[0] = last;
			let index = 0;
			while (true) {
				const left = index * 2 + 1;
				const right = left + 1;
				let smallest = index;
				if (left < this.values.length && this.values[left] < this.values[smallest]) smallest = left;
				if (right < this.values.length && this.values[right] < this.values[smallest]) smallest = right;
				if (smallest === index) break;
				[this.values[index], this.values[smallest]] = [this.values[smallest], this.values[index]];
				index = smallest;
			}
		}
		return minimum;
	}
}

function kthLargest(numbers, k) {
	if (k < 1 || k > numbers.length) throw new RangeError('invalid k');
	const heap = new MinHeap();
	for (const number of numbers) {
		heap.push(number);
		if (heap.values.length > k) heap.pop();
	}
	return heap.peek();
}

Top K frequent elements

Count each value, then place values into frequency buckets. Bucket index is the frequency, so scanning from the highest bucket downward returns the most frequent values without repeatedly sorting. This is O(n) average time and O(n) space when values are hashable.

function topKFrequent(values, k) {
	const counts = new Map();
	for (const value of values) counts.set(value, (counts.get(value) || 0) + 1);

	const buckets = Array.from({ length: values.length + 1 }, () => []);
	for (const [value, frequency] of counts) buckets[frequency].push(value);

	const result = [];
	for (let frequency = buckets.length - 1; frequency >= 0 && result.length < k; frequency -= 1) {
		for (const value of buckets[frequency]) {
			result.push(value);
			if (result.length === k) break;
		}
	}
	return result;
}

Product of array except self

Build the answer in two passes. The first pass stores the product of all values to the left of each position. The second pass multiplies by the product of values to the right. This avoids division, handles zeros correctly, runs in O(n), and uses O(1) extra space apart from the output array.
Dry run: For [1,2,3,4], the left products are [1,1,2,6]. Scanning from the right with suffix products 24,12,4,1 gives [24,12,8,6].
function productExceptSelf(numbers) {
	const result = Array(numbers.length).fill(1);
	let prefix = 1;
	for (let index = 0; index < numbers.length; index += 1) {
		result[index] = prefix;
		prefix *= numbers[index];
	}

	let suffix = 1;
	for (let index = numbers.length - 1; index >= 0; index -= 1) {
		result[index] *= suffix;
		suffix *= numbers[index];
	}
	return result;
}

productExceptSelf([1, 2, 3, 4]); // [24, 12, 8, 6]

Detect a cycle in a linked list

Use Floyd's tortoise-and-hare algorithm. A slow pointer advances one step and a fast pointer advances two. If they meet, the fast pointer has caught the slow pointer inside a cycle. If fast reaches null, the list is acyclic. This uses O(n) time and O(1) space.
Dry run: For 3 → 2 → 0 → -4 with the tail pointing back to 2, slow moves one node and fast two nodes per round. They eventually meet inside the loop. For a straight list, fast reaches null and the algorithm returns false.
function hasCycle(head) {
	let slow = head;
	let fast = head;
	while (fast && fast.next) {
		slow = slow.next;
		fast = fast.next.next;
		if (slow === fast) return true;
	}
	return false;
}

Number of islands in a grid

Scan every cell. When an unvisited land cell is found, increment the island count and run DFS or BFS to mark all connected land in four directions. The visited marking is the key invariant: each land cell is processed once, giving O(rows × columns) time and space proportional to the grid recursion or queue.
Dry run: On a grid containing a cluster of adjacent 1s, the first 1 starts one DFS. Its neighbors are converted to 0, so later scans do not count the same island again. A separated cluster starts a second DFS and increments the answer.
function numberOfIslands(grid) {
	if (!grid.length) return 0;
	const rows = grid.length;
	const columns = grid[0].length;
	let islands = 0;

	function visit(row, column) {
		if (row < 0 || row >= rows || column < 0 || column >= columns || grid[row][column] !== '1') return;
		grid[row][column] = '0';
		visit(row + 1, column);
		visit(row - 1, column);
		visit(row, column + 1);
		visit(row, column - 1);
	}

	for (let row = 0; row < rows; row += 1) {
		for (let column = 0; column < columns; column += 1) {
			if (grid[row][column] === '1') {
				islands += 1;
				visit(row, column);
			}
		}
	}
	return islands;
}

function kthSmallest(numbers, k) {
	if (k < 1 || k > numbers.length) throw new RangeError('invalid k');
	const sorted = [...numbers].sort((left, right) => left - right);

Explain cache-aside and its failure modes with a dry run.

Request 1 checks Redis and misses, reads MongoDB, then writes the result with a TTL. Request 2 reads Redis and avoids MongoDB. On an update, write MongoDB first, then invalidate the key. If invalidation fails, TTL limits staleness and a versioned key or event-driven invalidation repairs the cache. Redis must never be the only source of truth unless the business explicitly accepts that durability model.
